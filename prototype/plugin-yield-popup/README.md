# THROWAWAY: mobile popup/Yield feasibility probe

Question: With stock Herdr 0.9.0 and RootShell's upstream client-shell fallback, can a mobile user **see and interact with** a Herdr plugin popup while a VS Code official direct attach may still hold the Pane resize lock?

The plugin cannot release VS Code control directly, send Pane input, or change geometry. It shows a popup with a `y`/`q` prompt. A manual CLI open auto-exits after 3 minutes and **cannot Yield**; when auto-opened by the VS Code prototype with `HERDR_VSCODE_POPUP_SOCKET`, it receives heartbeats and exits on socket loss or after about 4 seconds without a heartbeat. Pressing `y` sends a generation-bound request to VS Code. After acknowledgment, VS Code rechecks its owned visible attach and **Yields its control in the throwaway prototype**; mobile input/geometry and VS Code reacquisition remain to be tested live. The plugin never terminates the Pane itself.

A local `herdr plugin link` registers plugins **globally for the current user**, across Sessions. The owner consented to temporary linking on 2026-09-24, and the plugin was unlinked after the successful live gate; `herdr plugin list --json` then returned an empty list. Do not relink without renewed consent. If temporarily linked for another check, unlink with `herdr plugin unlink local.vscode-yield-popup-probe` afterwards. Do not install from GitHub or alter the user's Herdr config. If a popup is still visible, press `q`. A manually opened popup also auto-closes after 3 minutes; a VS Code-offered popup should close promptly on Yield, losing eligibility or losing heartbeats. The popup is a temporary Herdr UI resource, not the target Pane; Yield must not stop its process.

First live check **passed** on 2026-09-24: after `herdr --session default plugin pane open --plugin local.vscode-yield-popup-probe --entrypoint confirm` returned `ok`, the user on RootShell mobile saw the popup, pressed `y`, saw the confirmation and the popup closed after three seconds. This proves a server-opened popup is visible and accepts input on mobile against the current stock Herdr setup. A second host-opened popup also worked on RootShell mobile while the user had opened the node-pty direct-attach prototype. The supplied VS Code Output shows direct attach ready at 15:11:59 and released at 15:13:55 when the active terminal changed to zsh; the exact popup-open instant is not independently timestamped, so correlating the popup press to that attach interval would make the lock-specific claim stronger. The mobile user did **not** initiate these earlier popups: both opens were from the host CLI. The next experiment instead has VS Code open the popup automatically while its Pane editor is active, so RootShell does not need a plugin-action UI. Whether a popup stays available while RootShell is disconnected, affects Ghostty, or disappears on VS Code loss remains to be checked live. In this run ordinary selection and Shift+Enter worked in direct attach, but Pi wheel scrolling did not; the prototype's isolated `[ui] mouse_capture=false` may suppress host wheel when the application does not request mouse reporting. Do not treat terminal fidelity as fully passed in this Pane state. Do not build VS Code signalling before both gates pass.
