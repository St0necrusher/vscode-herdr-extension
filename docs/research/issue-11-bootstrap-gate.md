# Research: issue #11 §10.1 bootstrap gate — Herdr v0.9.0 / protocol 22

## Decision update (2026-09-18)

This report remains the factual v0.9.0/protocol 22 baseline, but its original strict gate is superseded by the owner decision recorded in [`issue-24-herdr-switcher-audit.md`](./issue-24-herdr-switcher-audit.md). Issue #11 will use subscribe-first snapshot reconciliation: subscribed events invalidate the current projection and trigger a coalesced full snapshot replacement. The first implementation will not replay event payloads, compute snapshot diffs, or claim a universal loss-free event guarantee. The silent 512-event overflow remains an accepted low-probability limitation rather than an implementation blocker.

## Original summary

Under the original universal-authority requirement, the gate was **not cleared**. The v0.9.0 tag (annotated tag `cca4af8…`, commit `b99002a…`) does document subscribe-first/snapshot-second and its source establishes a server-side subscription start point, but protocol 22 is one-request-per-connection, has a silently bounded 512-event hub, lacks a wire cursor/instance identity, and cannot globally subscribe to `pane.agent_status_changed`. Therefore that stricter design could not claim a universally coherent authoritative projection or prove that its physical sockets reach the same server generation.

Issue #23 at local commit `b604743df0a067c54febfc814d4a472395d5c689` matches the feature-ownership baseline described in `docs/design/issue-11-connect-bootstrap-session.md`; no #23 implementation mismatch was found. The mismatches below are in the proposed §10 protocol design, not product decisions.

## Findings

1. **Claim (critical): protocol 22 requires distinct physical connections not only for `events.subscribe` versus `session.snapshot`, but also for `ping` versus `session.snapshot`; the current design's reusable “request transport” is unsupported.** The version-matched docs explicitly say to open `events.subscribe` “on another connection” and buffer it while calling `session.snapshot`. More decisively, the v0.9.0 server reads exactly one initial request, dispatches subscription requests into a stream loop, and for an ordinary request writes one response and returns; it never reads a second request from that connection. Consequently the safe topology for the design's validation sequence is at least three sequential/concurrent physical connections: ping, subscription, snapshot. `docs/design/issue-11-connect-bootstrap-session.md` §§10.3 and 10.6 currently imply ping and snapshot can share one request transport, and §10.2 discusses multi-request/out-of-order correlation that the target server does not support on an ordinary socket. **Sources:** [v0.9.0 socket docs](https://github.com/herdrdev/herdr/blob/b99002ac99b09e00b4ca692436cb15a6b0d676f1/docs/next/website/src/content/docs/socket-api.mdx), [server dispatch](https://github.com/herdrdev/herdr/blob/b99002ac99b09e00b4ca692436cb15a6b0d676f1/src/api/server.rs#L148-L286). **Support:** direct evidence plus interpretation. **Confidence:** high.

2. **Claim (high): lifecycle subscription eligibility begins at a server-side sequence capture, before acknowledgement; acknowledgement is sent only after all subscription objects/probes are constructed.** `stream_subscriptions` captures `event_hub.current_sequence()`, constructs every `ActiveSubscription` using that floor, writes `subscription_started`, and only then enters polling. Ordinary lifecycle subscriptions initialize `last_sequence` to that captured value, so events with a higher internal sequence during setup/ack are eligible. This is not identical to the client-side phrase “after the subscribe request is written”: events occurring after client write but before the server captures its sequence are intentionally outside the stream (though a later snapshot should normally contain their effects). Parameterized agent-status subscriptions choose a later sequence around their probe, so they do not share exactly the same boundary as ordinary lifecycle filters. **Sources:** [server subscription setup](https://github.com/herdrdev/herdr/blob/b99002ac99b09e00b4ca692436cb15a6b0d676f1/src/api/server.rs#L698-L758), [subscription construction](https://github.com/herdrdev/herdr/blob/b99002ac99b09e00b4ca692436cb15a6b0d676f1/src/api/subscriptions.rs#L91-L224). **Support:** direct evidence. **Confidence:** high.

3. **Claim (critical): the documented snapshot-plus-FIFO algorithm is the intended v0.9.0 contract, but the source does not support an unconditional correctness/authority claim.** The tag-matched docs prescribe: acknowledge subscription, buffer it, take/install snapshot, replay buffered events in order. Internally, events have monotonically increasing sequence values and lifecycle polling is FIFO. However, the hub retains only 512 events, silently drops older entries, exposes no gap to the client, and wire events carry no cursor. A slow subscriber or sufficiently high mutation rate can therefore lose eligible events with no detectable recovery trigger. Idempotence does not repair a missing event, and finite probes cannot establish absence of this execution. **Sources:** [v0.9.0 socket docs](https://github.com/herdrdev/herdr/blob/b99002ac99b09e00b4ca692436cb15a6b0d676f1/docs/next/website/src/content/docs/socket-api.mdx), [bounded EventHub](https://github.com/herdrdev/herdr/blob/b99002ac99b09e00b4ca692436cb15a6b0d676f1/src/api/event_hub.rs#L1-L40), [FIFO lifecycle poll](https://github.com/herdrdev/herdr/blob/b99002ac99b09e00b4ca692436cb15a6b0d676f1/src/api/subscriptions.rs#L273-L283), [protocol-22 schema](https://github.com/herdrdev/herdr/blob/b99002ac99b09e00b4ca692436cb15a6b0d676f1/docs/next/api/herdr-api.schema.json). **Support:** direct evidence plus researcher inference about overflow. **Confidence:** high.

4. **Claim (critical): subscribed lifecycle coverage is insufficient for the proposed coherent snapshot projection.** Workspace/worktree/tab/pane/layout lifecycle filters exist globally, but `pane.agent_status_changed` requires a concrete `pane_id`; the protocol offers no wildcard/global variant and a streaming socket accepts only its initial fixed subscription request. A client cannot subscribe to all future panes before taking the snapshot. `pane.agent_detected` is global but does not replace status/presentation changes, and the snapshot includes an `agents` array. Thus §10.4's plan to subscribe to Agent-status changes as though they were a global lifecycle filter is not implementable from the protocol-22 schema, and the full projection can become stale. **Sources:** [subscription enum](https://github.com/herdrdev/herdr/blob/b99002ac99b09e00b4ca692436cb15a6b0d676f1/src/api/schema/events.rs#L10-L82), [subscription implementation](https://github.com/herdrdev/herdr/blob/b99002ac99b09e00b4ca692436cb15a6b0d676f1/src/api/subscriptions.rs#L91-L224), [snapshot shape](https://github.com/herdrdev/herdr/blob/b99002ac99b09e00b4ca692436cb15a6b0d676f1/src/api/schema/session.rs#L8-L23). **Support:** direct evidence plus interpretation. **Confidence:** high.

5. **Claim (critical): protocol 22 provides no server-instance/generation identity capable of proving that separate ping/subscription/snapshot sockets hit the same running server.** `pong` exposes version, protocol and capabilities. `endpoint_protocol_generation` is documented as a stable client-owned endpoint protocol generation and is populated from a compile-time protocol constant; it is compatibility metadata, not a per-process incarnation. `session.snapshot` repeats only version/protocol and has no instance ID or event cursor. Socket-file identity exists only inside server lifecycle/cleanup and is not returned. The tag-matched handoff docs also state that client sockets and subscription streams may be interrupted during replacement; equal `0.9.0`, protocol `22`, and endpoint generation `1` do not identify one process. **Sources:** [server capability shape](https://github.com/herdrdev/herdr/blob/b99002ac99b09e00b4ca692436cb15a6b0d676f1/src/api/schema/server.rs#L15-L27), [pong construction and internal socket identity](https://github.com/herdrdev/herdr/blob/b99002ac99b09e00b4ca692436cb15a6b0d676f1/src/api/server.rs#L85-L122), [snapshot shape](https://github.com/herdrdev/herdr/blob/b99002ac99b09e00b4ca692436cb15a6b0d676f1/src/api/schema/session.rs#L8-L23), [v0.9.0 handoff semantics](https://github.com/herdrdev/herdr/blob/b99002ac99b09e00b4ca692436cb15a6b0d676f1/docs/next/website/src/content/docs/session-state.mdx). **Support:** direct evidence plus interpretation. **Confidence:** high.

6. **Claim (info): version matching is established for the inspected material; current web docs are corroborative only.** GitHub resolves tag `v0.9.0` to commit `b99002ac99b09e00b4ca692436cb15a6b0d676f1`. That tag contains `docs/next/api/herdr-api.schema.json` declaring protocol 22 and the quoted socket guide. There is no archived `docs/versions/0.9.0` directory in the tag, so `docs/next` at the release commit is the closest version-matched documentation. The live page at `https://herdr.dev/docs/socket-api/` currently says similar things, but it is unversioned and was not used to establish target behavior. **Sources:** [tag object](https://api.github.com/repos/herdrdev/herdr/git/tags/cca4af8dfad160bc5fb5ae133b70882b5fe28f61), [tag schema](https://github.com/herdrdev/herdr/blob/b99002ac99b09e00b4ca692436cb15a6b0d676f1/docs/next/api/herdr-api.schema.json), [current web docs](https://herdr.dev/docs/socket-api/). **Support:** direct evidence. **Confidence:** high.

7. **Claim (info): issue #23 implementation at `b604743` matches the #11 design's prerequisite host-ownership baseline; no mismatch found.** Local git history identifies HEAD as `b604743df0a067c54febfc814d4a472395d5c689`. `src/features/sessions/VsCodeSessionsFeature.ts:1-46` composes host-neutral `SessionsFeature` with feature-owned VS Code children and owns their disposal; `src/features/sessions/vscode/VsCodeHerdrStatusView.ts:1-58` and `VsCodeHerdrCommandRegistry.ts:1-36` contain direct VS Code API use; `src/features/sessions/index.ts:1-2` exports the host composition through the ordinary feature barrel; `src/extension/HerdrExtension.ts:1-38` imports it through `#features/sessions`, injects external infrastructure, and disposes only the feature and shared logger. `eslint.config.mjs` also encodes the matching boundaries and VS Code import restrictions. **Sources:** local files at the stated commit; `docs/design/issue-11-connect-bootstrap-session.md` §§4, 6, 14. **Support:** direct evidence. **Confidence:** high.

## Contradictions

- **Documentation versus implementation limit:** the v0.9.0 guide presents buffered replay as gap-avoiding, while the implementation silently truncates the shared event history after 512 records and gives clients no cursor/gap indication. The algorithm is an intended contract but not a universal guarantee under the inspected implementation.
- **§10.5 wording versus server boundary:** the design says events after the client writes subscribe are buffered; the server only makes ordinary lifecycle events eligible after its own later `current_sequence()` capture.
- **§§10.2/10.3/10.6 versus server transport:** the design anticipates a reusable request transport and out-of-order response correlation; v0.9.0 handles one initial request per ordinary connection.

## Missing evidence

- No protocol-22 field or operation was found that binds ping, subscription and snapshot to one server incarnation.
- No wire sequence/cursor, overflow error, resnapshot trigger, or documented maximum event rate was found.
- No global/wildcard agent-status subscription or way to add subscriptions to an existing stream was found.
- No disposable live-v0.9.0 probe was run. Such a probe could observe selected interleavings but would not resolve the universal overflow, coverage, or generation-identity blockers.
- Source-level ordering between every possible state mutation, event emission, and snapshot capture was not exhaustively audited; that work would not remove the explicit blockers above.

## Next steps

1. Treat §10.1 as blocked until the design records an explicit non-authoritative limitation or Herdr supplies protocol support for instance identity, detectable replay gaps/cursors, and complete global lifecycle coverage.
2. Correct the physical topology for v0.9.0 to one ordinary request per connection (including separate ping and snapshot sockets) before implementation planning.
3. If Herdr upstream changes are possible, request a snapshot/event cursor plus server-incarnation ID and a global agent-status lifecycle stream; then re-audit against an exact release tag/schema.
