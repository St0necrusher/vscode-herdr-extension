# Slice 0b: real-composition extension test against a fake herdr

Read `docs/design/issue-66-architecture-migration/briefs/common.md` first; it applies here.

**Worktree:** `/Users/kuzmichev/dev/vscode-herdr-extension-66-0b` (branch `refactor/66-0b`). Work only there. Slice 0a runs at the same time in another worktree on different files.

## Goal

No test exercises the real composition in `src/extension/HerdrExtension.ts`: every extension test builds its own features with fakes. Every migration slice rewrites that composition. Add one VS Code suite that activates the real extension against a fake `herdr` and checks the main scenario end to end, so a wiring mistake in any later slice fails a test.

Production code under `src/` does not change. If the scenario cannot be driven without a production change, stop and report.

## Scenario

With the real extension activated in a fresh window whose `herdr.executable` points at a fake herdr:

1. The Session becomes connected: the status bar item and the Sessions view show the connected Session.
2. The selected Session is persisted in `workspaceState` (observe it through behavior, e.g. a later activation or a command that depends on it, or skip with a reason if the host offers no way).
3. The Spaces and Panes of the fake snapshot are visible through the real tree data providers (`herdr.spaces`, `herdr.panes`), reached through the VS Code API, not by constructing views.
4. `herdr.openPane` for a Pane opens a Pane terminal editor.
5. A `pane.moved` event from the fake herdr rebinds that open editor (title or routing as `handlePaneMoved` defines).

## How

- The fake herdr is a Node script used as the executable: it answers the CLI calls the extension makes (`HerdrCliSessionDirectory`: list, resolve, start) and serves the JSON socket protocol (`src/infrastructure/herdr/socket/`). `test/integration/herdr-socket/JsonSocketHerdrSessionConnection.test.ts` already fakes the protocol; reuse its knowledge, not its file. Observe/attach clients may spawn the executable too (`src/infrastructure/pane-editors/HerdrPane*.ts`); the fake needs only what the scenario reaches.
- Isolate the test from any herdr on the developer's machine: the fixture workspace sets `herdr.executable` to the fake explicitly. VS Code on macOS inherits the login shell environment, so a real herdr is on `PATH` locally.
- Give the suite its own fixture workspace and its own `.vscode-test.mjs` config entry (like `fresh-window`), so its activation does not interfere with the other suites.
- Add its build entry in `esbuild.mjs`. If the fake herdr script needs bundling or an executable bit, handle that in the build or the fixture.
