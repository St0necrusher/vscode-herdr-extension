## 1. Что важнее всего проверить

### Ответственности, а не только пути импортов

Главная цель — простые правила и понятные владельцы. Новые каталоги сами по себе не доказывают достижение цели.

Проследите несколько полных путей: запуск npm-скрипта; создание Space с открытием Pane; закрытие группы с закрытием редакторов; открытие Pane агента; потеря соединения с сохранением Stale-снимка. Для каждого пути должно быть понятно:

- API выполняет взаимодействие с Herdr и обеспечивает корректность получаемых данных.
- Модуль владеет состоянием, ресурсом и предметными правилами.
- Фича владеет последовательностью действий, подтверждением и результатом.
- View предоставляет ввод и отображение, а не скрытый сценарий.
- Extension связывает объекты, но не вычисляет доступность действий, выбранный Space или актуальность данных.

Особенно важно проверить, не распался ли старый Navigation на множество файлов, между которыми всё ещё нужно мысленно собирать один сценарий. Сценарий должен читаться локально; повторяющееся техническое связывание не должно заслонять его действия.

### Единственная власть над состоянием

Убедитесь, что перенос не добавил второй снимок, store выбора или отдельную машину состояния проекции. Производное значение допустимо; независимо изменяемая копия — нет.

Selected Session остаётся у Sessions; Selected Space — у Workspace Context с привязкой к Session. Присутствие и фокус редакторов остаются фактами владельца редакторов. Потребитель не должен восстанавливать актуальность снимка из внутренних этапов подключения.

### Реальные зависимости при загрузке

Проверяйте не только TypeScript-типы и ESLint, но и runtime-цепочку публичных экспортов. Чистая модель должна загружаться без VS Code. Подмена barrel в тесте не исправляет production-зависимость. Случай D16 уже показал, что чистая функция за host-зависимым публичным входом нарушает эту цель.

### Порядок и момент чтения фактов

Сохранённые assertions не доказывают сохранение всей семантики. Проверьте момент чтения Session, Space, executable и снимка до/после await; порядок публикации связанных фактов; закрытие редакторов только после успешного закрытия объектов Herdr. Не меняйте поведение в review без отдельного решения, даже если новая последовательность кажется безопаснее.

### Размер архитектурных накладных расходов

Для каждого нового класса, интерфейса, фабрики и helper спросите: какую самостоятельную обязанность он имеет? Класс, который регистрирует команды и освобождает регистрации, имеет реальный lifecycle. Класс, который только передаёт вызов следующему классу, требует другого основания.

Проверьте, не появились ли универсальные регистраторы команд, сервисы именования, несколько обёрток над settings, фабрики единственного статического объекта или проверки гипотетических отказов. Восстановление поведения не требует такой инфраструктуры.

## 2. Решения с наибольшим риском

### D10: локальные контракты модулей

Это разрешение на узкую структурную зависимость, а не способ скрыть произвольную связанность. Если локальный контракт копирует почти весь публичный API Sessions, или модули вызывают друг друга в обе стороны, запрет peer-импортов соблюдён только формально.

Проверьте минимальность контрактов, отсутствие прямых импортов peer-типов и отсутствие runtime-обёрток ради одного TypeScript-типа. Дублирование небольшого структурного типа может быть ценой запрета peer-импортов; дублирование преобразований, политик и mutable state этой ценой не является.

### D16–D17: имя Pane и сборка запроса открытия

Это самый явный компромисс, который я прошу перепроверить. Моё первое размещение paneName в Pane Editors оказалось неудачным из-за host-зависимого barrel. Перенос в Sessions обоснован тем, что функция выводит имя из данных Pane, а не из состояния редактора. Но доступность в Vitest сама по себе не является предметным основанием размещения.

Проверьте, что Sessions действительно остаётся владельцем правил над данными снимка, а не становится складом любых чистых функций. Не переносите функцию обратно автоматически и не обходите проблему mock-ом.

После передачи готового имени paneTerminalOpenRequest может оказаться лишь короткой упаковкой четырёх полей. Проверьте пользу такого публичного helper: уменьшает ли он реальное повторение и удерживает ли стабильный смысл запроса? D17 не является доказательством, что helper обязан существовать вечно. Если он только заставляет каждый сценарий делать дополнительные вызовы без полезной границы, отметьте это как кандидат на упрощение с конкретным сравнением вариантов. Не вводите сервис именования или peer-импорт для его сохранения.

### D13 и правило shared/

Пользователь явно выбрал строгие направления внутри блока. Не предлагайте отмену правила только потому, что прямой импорт короче.

Однако проверьте, что shared/ содержит действительно общие части, а не всю реализацию блока, перемещённую туда ради lint. Protocol должен находиться у текущего владельца; не надо поднимать его ради будущих потребителей. Barrel должен открывать нужное, а не экспортировать всё транзитивно. Разбиение api/herdr на несколько API-блоков только для обхода внутреннего запрета также противоречит замыслу.

### D6: настройки

Общий механизм Core должен оставаться маленьким и не знать ключи Herdr. Extension связывает механизм с ключами, но не должен забирать правило приоритета выбранной Session. API получает нужный executable, не весь объект настроек приложения.

Риск — несколько новых адаптеров вокруг двух строк или фиксация executable при запуске вместо прежнего чтения перед операцией. Проверяйте простоту и временную семантику одновременно.

### D18: команды и структурные аргументы

Удаление instanceof было намеренным. Это не разрешение расширить доступность действий. Проверьте различия между закрытием Tab-группы и строки Pane, текущий Selected Space, connected/Stale, отсутствующий объект, пустой аргумент и фактический payload команды из меню.

Не требуйте восстановления зависимости от View-классов. Нужные ограничения выражаются через данные и текущие правила. Не добавляйте общий валидатор всех команд, если достаточно нескольких локальных проверок.

### D15: проекция без фасада

Прямое предоставление проекции владельцем состояния — целевое решение. Риск только в реализации: второй emitter, копия проекции или иной порядок подписок способны изменить наблюдаемую последовательность. Должно остаться преобразование существующего состояния и уведомлений, а не ещё один владелец.

### D8: takeover

Известная регистрация plugin в API допустима как техническое состояние внешней интеграции. Она не должна выдавать желаемое состояние за подтверждённое или владеть политикой предложения takeover. Решение о предложении принадлежит редактору; сообщения пользователю — фиче.

Не включайте исправление известного бага #67 в эту миграцию. Отметьте его как унаследованное ограничение, если оно влияет на вывод review.

### D4: SessionsModel как единый объект

Это сознательное ограничение миграции, не доказательство идеальной декомпозиции. Разделение владельцев отложено в #68. Большой размер файла сам по себе не является основанием блокировать PR. Основание для замечания — новая смешанная ответственность, добавленная миграцией, либо нарушение уже принятой границы API/Modules.

## 4. Критерий результата review

Разделите выводы на три группы:

1. Нарушение принятого намерения или новое усложнение миграции — исправить в PR с точным примером.

Проверка относится к HEAD `425ada2` worktree `vscode-herdr-extension-66`. A–F проверены также отдельным read-only агентом; G–L проверены мной по исходникам. Это архитектурные вердикты, не результат запуска тестов. Код не изменён.

## A. StartLocalSessionFeature

**Вердикт: реальный дефект против намерения; исправить в этом PR.**

`StartLocalSessionFeature.ts:7–13` только регистрирует команду и передаёт вызов `startSelectedSession()`. `ConnectionStatus.ts:18–19,71–72` уже получает нужные операции. Отдельный сценарий локального запуска был предусмотрен планом 2b, но фактическая реализация не содержит отдельной сценарной обязанности. Моё прежнее согласие с каталогом не требует сохранять пустую прослойку.

Предпочитаю удалить фичу. `ConnectionStatus` регистрирует `herdr.start`, вызывает операцию напрямую и освобождает регистрацию. Его кнопка Start использует ту же операцию. Сохранить семантику ошибок и возврата Promise. Проверки маршрутизации и освобождения перенести на нового владельца, не удаляя проверяемое поведение. Изменение ожидания числа команд владельца допустимо как следствие этого решения; полный набор команд расширения не меняется.

## B. Старые типы Sessions

**Вердикт: реальные остатки миграции; исправить в этом PR.**

В `sessionEvents.ts` интерфейс источника и имя события не нужны production-потребителям. Map используется в двух местах `SessionsModel.ts:54,158`, но содержит только `pane.moved`. Заменить эти типы на уже используемый `HerdrPaneMovedEvent`, удалить файл. Это не удаление события или подписки.

Удалить неиспользуемый `ActiveSessionProjectionSource` из `modules/sessions/activeSessionProjection.ts`. Сохранить состояние, функцию проекции и методы SessionsModel. Тест свежего окна может использовать контракт реального потребителя или локальный тестовый тип; не сохранять production-интерфейс только ради этого теста. Уточнение: в этом HEAD перечисленные event-типы уже не экспортируются из публичного входа Sessions; замечание относится к оставшимся определениям.

Удалить названные re-export из верхних `index.ts`: источники Workspace Context, `PaneEditorPresence` из Pane Editors, `HerdrConnectionFailureError` и `HerdrSessionProjectionConsumer` из API, если они не имеют внешнего production-потребителя в исправляемом diff. Не удалять внутренние определения: ошибка и consumer используются внутри API, а источники — внутри своих модулей. Тестам разрешены прямые импорты определений. D13 разрешал экспорт ошибки при необходимости; он не обязывает держать его без потребителя.

## D. Копии errorMessage/showError

**Вердикт: реальное избыточное дублирование, увеличенное миграцией; исправить в этом PR.**

`errorMessage` одинаково реализован в 12 файлах Features. Это техническое преобразование, а не расходящиеся сценарные правила. Вынести одну чистую функцию в Core и использовать её в перенесённых сценариях. Для одинаковых `showError` внутри одного feature-блока достаточно локального `shared/`; ещё проще убрать одноразовую обёртку и вызвать `void vscode.window.showErrorMessage(...)` на месте. Не создавать сервис уведомлений или общий обработчик всех ошибок.

Текст сообщения, решение о его показе и catch остаются в сценарии. Сохранить текущую обработку Promise. Точный счёт: `showError` есть в 11, а не 12 feature-файлах; вывод от этого не меняется. Это не требование устранить любую похожую строку во всём репозитории.

## E. Feature вызывает NpmScripts View

**Вердикт: реальное нарушение направления ответственности; исправить в этом PR.**

`RunNpmScriptFeature.ts:7,17,25–27` получает View как `NpmScriptCursorSource`; `HerdrExtension.ts:143` связывает их. Структурный тип скрывает обратную зависимость, но не устраняет её. Активный редактор и положение курсора относятся к адаптеру ввода.

Предпочитаю вариант 1: `VsCodeNpmScriptsView` регистрирует и освобождает команду-адаптер `herdr.runNpmScriptAtCursor`, получает target и передаёт его публичной операции фичи. Фича владеет выполнением сценария, но не запрашивает target у View. Если View нужен `NpmScriptTarget`, пусть использует публичный тип входа фичи; фича не импортирует View. Порядок сборки меняется по новой направленной зависимости: сначала фича, затем View.

Уточнить правило регистрации одной фразой при необходимости: «View может регистрировать команду-адаптер, которая извлекает данные поверхности и передаёт их фиче; фича владеет выполнением сценария». Это узкое уточнение уже принятого разделения, не разрешение сценарной логики во View. Сохранить прежние отсутствие target, сообщения и момент чтения курсора. Не переносить parser в Core только ради устранения этого цикла.

## F. Регистрация decorations в Extension

**Вердикт: реальное несоответствие владельца поверхности; исправить в этом PR.**

`visiblePaneEditorDecoration.ts:19–35` владеет данными и подписками, но регистрация находится в `HerdrExtension.ts:145–146`. Перенести её в существующего владельца decorations. Его dispose освобождает регистрацию, подписки и emitter. Extension создаёт один объект и владеет только им. Не вводить дополнительный класс-обёртку ради регистрации.

Тестовые сборки, регистрирующие provider вручную, обновить: одна регистрация на экземпляр. Проверки поведения сохранить.

## G. Учёт ресурсов в HerdrExtension

**Вердикт: реальное усложнение, увеличенное миграцией; упростить в этом PR. Сам cleanup не является дефектом.**

В исходной версии тоже был catch с освобождением, но теперь перечни полей, временных переменных, присваиваний и dispose многократно повторяют около двух десятков ресурсов. Это скрывает сборку приложения. Внешне значимые регистрации и тест очистки при частичной ошибке уже существуют, поэтому просто удалить catch нельзя.

Предпочитаю один небольшой локальный механизм учёта полученных disposable-ресурсов с общей процедурой освобождения. Поля оставить только для объектов, нужных после конструктора, прежде всего Sessions и инициализации plugin; прочие зависимости связывать локальными const. Записывать владение сразу после успешного создания. В catch освобождать уже полученные ресурсы и повторно бросать исходную ошибку; обычный dispose использует тот же механизм и остаётся идемпотентным.

Не вводить DI-container, универсальный lifecycle framework, async-dispose или новую изоляцию исключений. Важная оговорка: текущий порядок освобождения не является точным обратным порядком конструирования — popup освобождается между surfaces и focus tracker. Не заменять его слепо на reverse массива. Сохранить действующий порядок освобождения явным порядком в едином списке либо отдельно обосновать и проверить его изменение. Упрощаем запись владения, а не меняем lifecycle. #67 остаётся вне задачи.

## H. Нормализация настроек

**Вердикт: не дефект.**

`HerdrSettings.ts:8–15` связывает настройки хоста с типизированным входом приложения: trim и значения по умолчанию для пустых полей. Это допустимая деталь адаптации по D6. Продуктовое правило приоритета сохранённого выбора Session над настройкой остаётся у Sessions.

Перенос этой короткой нормализации в Sessions не улучшает границу и навязывает ему знание формата ввода VS Code. Никакой дополнительный объект нормализации не нужен.

## I. Узкие ролевые интерфейсы

**Вердикт: не дефект в приведённых примерах.**

`SessionsStateSource`, `SessionsOperations`, creation/management, selection, opening/closing описывают разные роли потребителя, а не зеркалят один класс целиком. IMPLEMENTATION разрешает интерфейс реальной границы, в том числе при одном поставщике. D10 не требует удалить интерфейсы Features → Modules.

Передача одного объекта в две роли может выглядеть многословно, но сохраняет минимальную поверхность каждой зависимости и не создаёт runtime-посредников.
